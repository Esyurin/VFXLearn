# 프로젝트 보충 리뷰 기준

이 문서는 `UnityAICodeReviewGuidelines.md`를 보충하는 프로젝트 고유 기준이다.
중요도(P0~P3), 지적 사항 형식, 출력 순서는 `UnityAICodeReviewGuidelines.md`를 따른다.

## 가독성과 유지보수성

### 이름을 통해 의도를 알 수 있는가?

* 클래스, 메서드, 변수 이름이 실제 역할을 명확하게 나타내는지 확인한다.
* `data`, `value`, `temp`, `manager`처럼 의미가 지나치게 넓은 이름이 남용되지 않았는지 확인한다.
* `bool` 변수는 상태를 자연스럽게 읽을 수 있는 이름인지 확인한다.

  * 예: `isDead`, `canAttack`, `hasTarget`
* 메서드 이름은 수행하는 동작을 동사 형태로 명확하게 표현하는지 확인한다.

단, 대소문자·접두사 같은 형식 규칙은 `.editorconfig`와 pre-commit이 검사하므로 지적하지 않는다.

### 매직 넘버를 사용하고 있지 않은가?

코드의 의미를 이름만으로 파악하기 어려운 숫자를 직접 사용하지 않았는지 확인한다.

```csharp
if (currentLevel >= 10)
{
    damage *= 1.5f;
}
```

`10`, `1.5f`가 게임 규칙에서 특별한 의미를 가진다면 상수나 설정값으로 분리하도록 제안한다.

```csharp
private const int SpecialLevel = 10;
private const float SpecialDamageMultiplier = 1.5f;
```

Unity Inspector에서 조정해야 하는 값이라면 `[SerializeField]`를 사용하는 방법도 고려한다.

```csharp
[SerializeField] private int specialLevel = 10;
[SerializeField] private float specialDamageMultiplier = 1.5f;
```

다음과 같이 의미가 명확하고 관용적으로 사용되는 값은 불필요하게 상수로 분리하지 않아도 된다.

* `0`: 초기화, 비어 있음, 최소값 검사
* `1`: 1만큼 증가, 기본 배율, 단위 방향
* `-1`: 검색 실패, 존재하지 않음을 나타내는 인덱스
* 반복문의 시작값과 증감값

다만 `-1`, `0`, `1`이라도 코드만 보고 의미를 파악하기 어렵다면 이름 있는 상수나 열거형으로 분리하도록 제안한다.

특히 다음 값이 코드 곳곳에 직접 작성되어 있다면 우선적으로 확인한다.

* 플레이어 체력과 공격력
* 이동속도와 회전속도
* 쿨타임과 지속시간
* 경험치와 레벨 기준
* 확률과 가중치
* 레이어 번호
* 애니메이션 상태 번호
* 최대 개수와 제한 횟수
* 데미지 배율
* 씬 인덱스

## 설계 참고 (부록)

아래 내용은 **명확한 문제가 확인될 때만** 근거로 삼는다. 규모가 작거나 변경 가능성이 낮은 코드에는 단순한 구조를 우선하며, 이 항목을 이유로 인터페이스, 패턴, 클래스 분리를 제안하지 않는다.

* **묻지 말고 시켜라**: 외부에서 객체의 상태를 가져와 판단한 뒤 행동을 결정하는 코드가 여러 곳에서 반복될 때, 객체에 행동을 요청하는 방식(`player.TakeDamage(damage)`)을 제안할 수 있다. 단순 조회가 자연스러운 UI 표시, 디버깅, 직렬화는 대상이 아니다.
* **응집도와 결합도**: 서로 관련 없는 기능이 한 클래스에 섞여 있거나, 작은 변경이 여러 클래스의 수정으로 번지거나, 클래스 간 순환 참조가 있을 때 개선 방향(어떤 책임을 어디로 옮길지, 이벤트·인터페이스·컴포지션 중 무엇이 적절한지)을 구체적으로 제안한다.
* **SOLID**:
  * SRP: 한 클래스가 입력, 이동, 공격, 체력, 애니메이션, 사운드, 저장, UI를 모두 처리하는 것처럼 책임이 명백히 과다할 때만 분리를 검토한다.
  * OCP: 종류가 계속 늘어나는 분기(`enemyType`)가 있고 실제로 확장될 예정일 때만 확장 구조를 제안한다.
  * LSP: 자식 클래스가 부모의 계약을 깨뜨리는 경우(예외로 막기, 의미 변경)를 확인한다.
  * ISP / DIP: 사용하지 않는 메서드를 구현하도록 강요받거나, 교체·테스트가 필요한 구현에 직접 의존할 때만 제안한다.
* 구조 개선을 제안할 때는 "현재 문제, 분리·추가할 클래스와 책임, 상호작용 방식, 장점과 비용"을 함께 설명한다.
